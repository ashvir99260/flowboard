### P00-03 application-shell choices (22 October 2026)

- **D37 — Compile Node apps in development.** Use `tsc-watch` 7.2.1 with the shared Nest/Node compiler settings and restart only after a successful compile. This preserves Nest decorator metadata and makes development match production output. Next.js uses its own development server and route type generation. The application manifests expose metadata, not public runtime APIs.
- **D38 — Honest, dependency-free shells.** The API has an empty Nest module and no custom routes before P01-02. The worker accepts and closes a TCP connection for process liveness only; it explicitly logs that queue work is unavailable until P11-02. The web renders a semantic, static setup page until P08-03. API/worker default to localhost and ports 3001/3002. Docker will supply its own host binding in P00-04.
- **D39 — Test compiled processes through real sockets.** Bootstrap tests use Node's test runner and a shared test-only process helper. A child-process preload rejects outbound connections, while the parent makes local HTTP/TCP requests. Tests require timely SIGTERM shutdown; Nest re-emits SIGTERM after completing its framework shutdown hooks, so that expected exit signal is accepted. Feature suites still use the planned Jest/Supertest/Playwright seams.
- **D40 — Cache Next output explicitly.** The web overrides the default `dist/**` output with `.next/**` excluding `.next/cache/**`. `next typegen` precedes standalone web type checking. Next telemetry is disabled for verification; no remote fonts or image downloads are required. Shared Next lint tooling declares its Next/React development dependencies so the parser resolves under strict pnpm isolation.

## D78 — Prisma migration and integration-test boundary

The database package uses Prisma 7's ESM client generator and PostgreSQL driver adapter. Generated sources stay local and are rebuilt by Turbo; only the schema and migration SQL are committed. The initial DDL migration is transactional. SQL supplies CHECK constraints, composite foreign keys, the current-refresh-family partial index and audit triggers. All 15 tables start with equal audit timestamps, reject changes to createdAt, and stamp updatedAt on every SQL update. Services avoid no-op updates.

Real PostgreSQL tests run in task-owned disposable Docker containers with random ports, independently of development or hosted URLs. Reconnect after restart rediscovers Docker's published port. API and worker images include OpenSSL so Prisma's migration engine selects the correct Linux binary. Optional source-generation commands need no database URL; migration commands require an explicit direct URL (falling back to DATABASE_URL only when deliberately supplied). Prisma's offline diff engine currently requires a syntactically valid explicit URL even when neither input connects to a database.

The schema does not enforce polymorphic scope-owner existence, full resolved field/status validity or authorization. Those remain the tested repository/service responsibilities in the following tasks.

## D79 — Tenant repository unit of work

Expose only typed read/write callbacks from the database package; retain Prisma and SQL internally. Every callback verifies membership from the database and rejects caller-provided role/extra context. Read bundles use a read-only Repeatable Read snapshot. Writes acquire the workspace lock under Read Committed, then reload membership so revocation committed by the previous lock holder is visible. Callback repository handles expire with the transaction.

Start with node/member/grant storage primitives, strict flat input allowlists and injected tenant selectors; add other repositories with their first use case. Permissions, revisions and outbox orchestration are service responsibilities, and no task write primitive is exposed yet. Global identity access is added with auth instead of an unused unrestricted API. Integration tests use a separate non-superuser role with CRUD on domain tables and no migration/DDL privileges. Public cursor signing is separate from internal ID-anchored storage reads.

## D80 — Atomic demo seed and portable API initialization

Keep migration/startup code in the database package and call it from the API before Nest listens. This works for local Docker and hosted Node entrypoints without maintaining a second shell bootstrap. A dedicated direct-connection advisory lock serializes the complete migration/seed sequence; Prisma keeps its own migration lock, and a separate transaction-scoped lock protects standalone demo creation. P06-03 reuses the existing task feature and strict placement union for POST move/reorder. A move keeps a status available at the destination, otherwise selects the first matching category using the resolver's position/key/ID lexical ordering. An explicit valid destination status overrides that default. No matching category rejects. Destination field validation requires explicit source-only clears and missing required values; retained assignees must still see the destination.

The server loads complete live source/destination columns, removes the target, inserts it at the requested edge/anchor, and assigns dense integer positions. Only changed rows advance version/audit time; the target's list/status/field/position changes combine into one update. Each changed row gets one task.updated event, including true previous/current list IDs, while the whole command advances dataVersion once and leaves configVersion unchanged. A list-only move has an explicit primaryListId change. No-ops preserve every revision; legacy gaps/ties normalize. Different targets may both succeed sequentially; same-target competing changes conflict only when the first actually changes its version.

PermissionService checks the source, destination and any anchor again inside the locked transaction. Reorder cannot change list/status. Before/after anchors must be distinct live tasks in the destination column. Full-column work is intentional at hobby scale; pagination never truncates placement calculations. Larger deployments can replace dense renumbering while retaining these API semantics.
