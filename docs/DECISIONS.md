### P00-03 application-shell choices (22 October 2026)

- **D37 — Compile Node apps in development.** Use `tsc-watch` 7.2.1 with the shared Nest/Node compiler settings and restart only after a successful compile. This preserves Nest decorator metadata and makes development match production output. Next.js uses its own development server and route type generation. The application manifests expose metadata, not public runtime APIs.
- **D38 — Honest, dependency-free shells.** The API has an empty Nest module and no custom routes before P01-02. The worker accepts and closes a TCP connection for process liveness only; it explicitly logs that queue work is unavailable until P11-02. The web renders a semantic, static setup page until P08-03. API/worker default to localhost and ports 3001/3002. Docker will supply its own host binding in P00-04.
- **D39 — Test compiled processes through real sockets.** Bootstrap tests use Node's test runner and a shared test-only process helper. A child-process preload rejects outbound connections, while the parent makes local HTTP/TCP requests. Tests require timely SIGTERM shutdown; Nest re-emits SIGTERM after completing its framework shutdown hooks, so that expected exit signal is accepted. Feature suites still use the planned Jest/Supertest/Playwright seams.
- **D40 — Cache Next output explicitly.** The web overrides the default `dist/**` output with `.next/**` excluding `.next/cache/**`. `next typegen` precedes standalone web type checking. Next telemetry is disabled for verification; no remote fonts or image downloads are required. Shared Next lint tooling declares its Next/React development dependencies so the parser resolves under strict pnpm isolation.

Sources: [Next installation](https://nextjs.org/docs/app/getting-started/installation), [Next CLI](https://nextjs.org/docs/app/api-reference/cli/next), [Nest application bootstrap](https://docs.nestjs.com/first-steps), [Nest shutdown lifecycle](https://docs.nestjs.com/fundamentals/lifecycle-events).

## Planning limitations

Package versions, executable commands and runtime performance are not verified by these documents. Phase 0 records pinned compatibility and adds real commands; Phase 12 validates the final clean Docker run. Documentation guardrails alone are not enforcement: lint, contract checks, integration tests and CI are explicit implementation tasks.

## Independent delivery choices (23 October 2026)

- **D41 — Application-specific tags and releases.** API, web and worker version independently. Runtime dependency changes propagate to their consumers; a build-only spec-export edge is not a reason to release an unchanged web app.
- **D42 — Publish immutable application artifacts from main.** Build each affected Docker image, record its source/digest and publish its GitHub Release in the same serialized workflow. Use the built-in GitHub token and resumable publication; no version-update commits or production database secrets are needed.
- **D43 — PostgreSQL locally, Neon when hosted.** Preserve the same PostgreSQL/Prisma model. Runtime and direct migration connection strings are server-side environment configuration; hosted seed remains opt-in. No cloud resources are provisioned by the release workflow.
- **D44 — Free-tier hosted deployment is a hobby target.** Proposed Vercel UI, Northflank API/worker/Redis and Neon PostgreSQL, subject to the user's host choice and current capacity. A free account does not imply a production SLA or permit silently enabling paid resources.

- **D45 — Release plans read committed artifact inputs.** Compare each app with its last published GitHub Release, using its runtime workspace closure, shared TypeScript configuration, source files, Dockerfile, build/start metadata and reachable resolved dependency snapshots. Include package-manager bootstrap documents in pnpm's YAML stream. Test/docs/lint-only files and development-only spec-export edges do not release consumers. Initial app publication is `0.1.0`; later changes use Conventional Commits. An unfinished older tag requires retrying that source before advancing; conflicting tags and divergent histories fail closed. Versioned artifacts are immutable, while package manifest versions stay private and unchanged.

- **D46 — User-selected hosted topology.** On 23 October 2026 the user selected Vercel UI, Northflank API/worker/Redis, and Neon PostgreSQL. GitHub automatically publishes per-app releases/images; provider accounts and deployment credentials remain unconnected. Deployments select an immutable app artifact independently. The current shells are not advertised as a completed hosted product.
- **D47 — Draft-first release recovery.** Build/push the immutable image, explicitly create its source tag, upload a source/digest manifest to a draft, then publish. Authenticated release listing recovers unpublished drafts. Require a clean checkout at the release SHA before image operations. PR validation has read-only permissions; only the serialized main publisher has package/content write access. Third-party actions are pinned to verified commit SHAs.

- **D48 — Deploy after publication, with explicit activation.** The user requested CI/CD in addition to releases. Keep the existing checks/publisher and add a main-only, serialized production job reconciling the latest published manifest of each app, with sources verified as ancestors of current main. Deploy Vercel by exact commit and Northflank by digest; do not depend on mutable tags or unverified webhooks. Missing provider credentials are a configuration error when CD is enabled. Keep CD disabled until credentials/targets are connected; P00-09 owns live acceptance.

- **D49 — Local Docker and deployment packaging are separate choices.** The user clarified that Docker is for local use and described a possible future trunk-based four-environment delivery flow. Keep local Compose; do not infer a requirement to deploy all hosted apps in containers or silently change hosts.
- **D50 — Build once, promote immutable bytes, inject target configuration at runtime.** Future `dev`, `qa`, `stage`, `prod` targets reuse an explicit candidate digest/version. A source SHA followed by a rebuild is insufficient. Use `APP_ENV` for target identity and production Node mode for hosted processes; public browser config is a safe dynamic bootstrap, with no environment-specific `NEXT_PUBLIC_*` substitution. [PROMOTION.md](PROMOTION.md) supersedes D48's production-only source-deploy assumption for this future requirement. The Vercel artifact path and four-environment implementation remain an explicit later decision.
- **D51 — Initial shared preview before four-environment promotion.** The user explicitly requested an initial preview on Vercel, Northflank and Neon. Replace D48's production target with a gated GitHub `preview` environment: Vercel builds the released SHA as a preview without production promotion; Northflank deploys released digests to dedicated preview services. Accept the Vercel source build for this initial stage only. D50 remains the future contract, not a prerequisite for preview activation. Use one shared preview to fit the hobby allocation; per-PR isolated databases/services are outside this task. Keep secrets server-side and do not claim that the current application shells implement the planned product.

Vercel forces the first project deployment to its production target. Initial preview setup therefore uses a dedicated `flowboard-preview` project with no actual production data/domains, and requires an explicitly reviewed bootstrap of the real app. The preview CI refuses an empty project before sending a deployment request. It does not create a dummy or intentionally failing bootstrap.

- **D52 — Parallel CI using free standard public-repository runners.** Run build, lint, tests, types and formatting as independent matrix jobs, with fail-fast disabled so one failure does not cancel other results. Each root command covers every applicable workspace via Turbo; dependency compilation remains ordered within each job where required. Docker acceptance starts alongside the matrix. Publication requires the entire matrix and Docker, then preview deployment follows publication. Use standard `ubuntu-24.04` runners only, without paid caching, larger runners or organization billing changes. Skip entry jobs if the repository becomes private, where standard-runner usage could become billable.

- **D53 — Local-only Graphify code index.** Reuse Graphify (`graphifyy` 0.4.23) as an optional developer tool, outside the pnpm/runtime dependency graph. Default to native cached AST extraction with `graphify update .`, without remote models or automatic semantic extraction. Commit only extraction filters, ignore rules and usage guidance; keep all generated graph/report/cache/memory data local. Codex reads the report and bounded query results to locate source, then checks current files and tests. Avoid global installations, settings changes and automatic hooks; missing or stale graphs never replace the canonical plan or block small edits.

- **D54 — Small local AI coding toolset.** Add pinned ast-grep as a root development tool for read-only structural searches. Reuse the available Serena connector for symbols/references and the installed Gitleaks CLI for local redacted secret checks. Reports belong under ignored `.ai-local/`; existing Serena state remains local. Keep generated output outside images and the Graphify corpus. No extra model service, paid integration, runtime package, global hook or automatic code rewrite is needed; current CI remains the authority for build/lint/type/test checks.

- **D55 — Optional, isolated Reverse Engineer Anything CLI.** Install the official `rea-agents@6.7.0` locally under ignored `.ai-local/rea/`, with its npm cache there too, update notifications and install scripts disabled and optional native instrumentation omitted. Keep it outside the workspace dependency/build graph: ordinary CI and Docker do not need reverse-engineering dependencies. Use static analysis of explicit owned JavaScript artifacts, save evidence under the same ignored directory and read bounded summary views. REA complements source navigation when the question concerns a built artifact; it does not replace source review. Do not run the upstream global agent setup or install native engines as part of this task. CLI readiness does not establish MCP registration; any future registration must preserve repository-local scope and existing settings.

- **D56 — Adapt product patterns within the fixed Flowboard architecture.** Use ClickUp-style hierarchy/configuration, Linear-style focused views and immediate feedback, and Asana's distinction between querying data and keeping clients current. Keep the existing NestJS modular monolith, PostgreSQL, generated REST client and one BullMQ worker. No proprietary database/schema claims, full client replica, EAV for core fields, extra hierarchy levels, multi-list tasks, sharding or microservice split is implied. The researched evidence and implementation design live in `REFERENCE_ARCHITECTURES.md` and `SYSTEM_DESIGN.md`; feature completion still needs the original tests.

- **D57 — Same-origin browser REST transport across preview hosts.** The browser calls generated SDK routes through web-origin `/api/v1`; a server-only Next.js route forwards to fixed runtime `API_INTERNAL_URL` plus `/v1`. This generic HTTP forwarding is a narrow transport exception to the handwritten-call restriction, not a second domain API/client. API remains the sole authentication, authorization and domain owner. Preserve host-only refresh cookies with Path=/, httpOnly, Secure in HTTPS and SameSite=Lax, without rewriting Domain. Check the original browser Origin against explicit allowed web origins; never trust arbitrary forwarded destination headers. No shared response cache, upstream redirects or arbitrary URL proxying. Direct `/v1` remains available to the cookbook/other clients. WebSocket clients connect directly to API using access JWTs, without refresh cookies. P07-04 implements this before P08-03; no proxy/auth implementation is claimed by this decision. This corrects the earlier assumption that credentialed CORS alone would make Lax cookies work across Vercel/Northflank default domains.

- **D58 — One conventional-commit policy for local hooks and CI.** Use pinned commitlint with the conventional preset. Install a tracked commit-msg hook only through an explicit repository-local command; preserve another configured hooks path and leave global settings unchanged. CI validates the PR title and actual head/base commit range from parsed event JSON, ignores standard merge commits deliberately, and handles first pushes without inventing a base. Run it in the existing lint matrix leg so publication remains gated without extra runners.
- **D59 — Shared lint rules with conservative ordering.** Reuse import-x, Next's React/accessibility/hooks rules and eslint-config-prettier; add compatible pinned Perfectionist, SonarJS, unused-import and JSON checks. Automate PascalCase for types/classes and JSX references; component declarations also follow it as a review convention. Do not rename every variable or external API key. Runtime object/JSX sorting is restricted to direct literal values; destructuring, positional parameters, overloads, meaningful arrays, side-effect evaluation and conditional export maps preserve order. Use one owner for each rule family and keep generated/local-tool data outside authored-source linting. See CODE_QUALITY.md for precise coverage and exceptions.
