### P00-03 application-shell choices (22 October 2026)

- **D37 — Compile Node apps in development.** Use `tsc-watch` 7.2.1 with the shared Nest/Node compiler settings and restart only after a successful compile. This preserves Nest decorator metadata and makes development match production output. Next.js uses its own development server and route type generation. The application manifests expose metadata, not public runtime APIs.
- **D38 — Honest, dependency-free shells.** The API has an empty Nest module and no custom routes before P01-02. The worker accepts and closes a TCP connection for process liveness only; it explicitly logs that queue work is unavailable until P11-02. The web renders a semantic, static setup page until P08-03. API/worker default to localhost and ports 3001/3002. Docker will supply its own host binding in P00-04.
- **D39 — Test compiled processes through real sockets.** Bootstrap tests use Node's test runner and a shared test-only process helper. A child-process preload rejects outbound connections, while the parent makes local HTTP/TCP requests. Tests require timely SIGTERM shutdown; Nest re-emits SIGTERM after completing its framework shutdown hooks, so that expected exit signal is accepted. Feature suites still use the planned Jest/Supertest/Playwright seams.
- **D40 — Cache Next output explicitly.** The web overrides the default `dist/**` output with `.next/**` excluding `.next/cache/**`. `next typegen` precedes standalone web type checking. Next telemetry is disabled for verification; no remote fonts or image downloads are required. Shared Next lint tooling declares its Next/React development dependencies so the parser resolves under strict pnpm isolation.

Sources: [Next installation](https://nextjs.org/docs/app/getting-started/installation), [Next CLI](https://nextjs.org/docs/app/api-reference/cli/next), [Nest application bootstrap](https://docs.nestjs.com/first-steps), [Nest shutdown lifecycle](https://docs.nestjs.com/fundamentals/lifecycle-events).

## Independent delivery choices (23 October 2026)

- **D41 — Application-specific tags and releases.** API, web and worker version independently. Runtime dependency changes propagate to their consumers; a build-only spec-export edge is not a reason to release an unchanged web app.
- **D42 — Publish immutable application artifacts from main.** Build each affected Docker image, record its source/digest and publish its GitHub Release in the same serialized workflow. Use the built-in GitHub token and resumable publication; no version-update commits or production database secrets are needed.
- **D43 — PostgreSQL locally, Neon when hosted.** Preserve the same PostgreSQL/Prisma model. Runtime and direct migration connection strings are server-side environment configuration; hosted seed remains opt-in. No cloud resources are provisioned by the release workflow.
- **D44 — Free-tier hosted deployment is a hobby target.** Proposed Vercel UI, Northflank API/worker/Redis and Neon PostgreSQL, subject to the user's host choice and current capacity. A free account does not imply a production SLA or permit silently enabling paid resources.

- **D45 — Release plans read committed artifact inputs.** Compare each app with its last published GitHub Release, using its runtime workspace closure, shared TypeScript configuration, source files, Dockerfile, build/start metadata and reachable resolved dependency snapshots. Include package-manager bootstrap documents in pnpm's YAML stream. Test/docs/lint-only files and development-only spec-export edges do not release consumers. Initial app publication is `0.1.0`; later changes use Conventional Commits. An unfinished older tag requires retrying that source before advancing; conflicting tags and divergent histories fail closed. - **D63 — Stable refresh family and fixed lifetime.** `RefreshSession` stores one row per single-use refresh credential. `familyId` is the stable JWT session identity; consumed rows remain for replay detection. - **D64 — Explicit inherited visibility and ordering versions.** `StatusOverride.hidden` is nullable: null inherits, true hides, false explicitly restores. ## D78 — Prisma migration and integration-test boundary

The database package uses Prisma 7's ESM client generator and PostgreSQL driver adapter. Generated sources stay local and are rebuilt by Turbo; only the schema and migration SQL are committed. The initial DDL migration is transactional. SQL supplies CHECK constraints, composite foreign keys, the current-refresh-family partial index and audit triggers. All 15 tables start with equal audit timestamps, reject changes to createdAt, and stamp updatedAt on every SQL update. Services avoid no-op updates.

Real PostgreSQL tests run in task-owned disposable Docker containers with random ports, independently of development or hosted URLs. Reconnect after restart rediscovers Docker's published port. API and worker images include OpenSSL so Prisma's migration engine selects the correct Linux binary. Optional source-generation commands need no database URL; migration commands require an explicit direct URL (falling back to DATABASE_URL only when deliberately supplied). Prisma's offline diff engine currently requires a syntactically valid explicit URL even when neither input connects to a database.

The schema does not enforce polymorphic scope-owner existence, full resolved field/status validity or authorization. Those remain the tested repository/service responsibilities in the following tasks.
