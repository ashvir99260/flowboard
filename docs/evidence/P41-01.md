# P41-01 List-first administration and details panels

Date: 30 October 2026
State: complete
Requirements: R179; preserve R160, R37 and R68.

## Work contract and design

The user selected right-hand details panels for Containers, Statuses and Custom Fields. Show an expandable space/folder/list hierarchy for containers and compact selectable rows for statuses and fields. Keep Add at the top right. Start with no editor open.

Use a non-modal, responsive two-column layout: the collection stays on the left and its editor opens on the right. At narrow widths show the editor before the collection. A centered popup was considered; the user chose the right-hand panel. An in-flow panel preserves existing sidebar navigation, scope selection and retained drafts without a backdrop or focus trap. Reuse current forms, generated operations, permissions, validation and conflict recovery.

Scope: shared settings presentation in `packages/ui`, administration/configuration views in `apps/web`, their browser tests, and the task/decision/requirement records. No backend, dependency, deployment or workspace lifecycle changes.

Failure cases: dirty Close/Escape must confirm; cancel retains edits; inactive panels cannot receive focus; scope/navigation retains existing behavior; stale configuration and failed saves keep drafts; narrow screens and long names must not overflow; members remain denied.

## Initial failures and corrections

The first browser run failed because the container hierarchy and named status details panel did not exist. The shared presentation check also failed before its exports existed. The UI source-layout gate then required the list row implementation to live in its own file; it was split without weakening that gate.

Source review found focus restoration gaps after saved configuration and when a selected container's ancestor was collapsed. Stable row IDs and visible-ancestor fallback now handle both. Visual review found compressed member columns; a keyboard-accessible horizontal scroll region keeps names and roles readable.

The complete suite exposed a real layout regression: a floating status notification covered an action in the right panel. Active panels now register inline notifications and release that registration when inactive. The original failing status workflow and a new browser story pass. The DOM-only harness verifies ownership; actual notification positioning is verified in Chromium because the DOM harness does not resolve the Emotion cascade consistently.

One intermediate browser run overlapped a rebuild and encountered the application's generic load error. That run was discarded, and subsequent browser checks ran only after the build finished. Full runs interrupted for fixes are not passing evidence.
