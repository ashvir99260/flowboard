# P02-14 — Database time for refresh-session creation

Date: 23 October 2026. State: complete. Requirement: R125. Gates: G01–G07 and G11.

RefreshSession audit defaults now use `dbgenerated("CURRENT_TIMESTAMP")`. Prisma supplies `now()` from the application host, while refresh consumption/revocation use PostgreSQL time. The new defaults keep those operations on one clock. The checked-in migration reasserts the two existing PostgreSQL defaults; it does not alter stored rows or lifecycle constraints. D94 records the choice.

## Acceptance evidence

- **pass — deterministic red/green:** new real-PostgreSQL tests failed before the change with host time 60 seconds ahead and behind. Creation fell outside the database time window in both cases. After generation with the new defaults, all eight refresh tests pass, including successful rotation, replay revocation and no remaining active family credential under either skew.
- **pass — real clocks and I/O:** only Date is faked, with actual timers, database operations and row locking retained. Fake time is restored in finally. Timestamp comparisons use the column's millisecond precision.
- **pass — expiry semantics:** the existing expiry test waits using PostgreSQL's clock instead of a host/DB time subtraction. Fixed family expiry, rollback, membership denial and logout coverage remain.
- **pass — migration inspection:** Prisma's configured schema comparison reports only two ALTER COLUMN SET DEFAULT CURRENT_TIMESTAMP operations. The migration matches those operations. Applying it to an isolated database containing a session preserves the entire row and both defaults.
- **pass — review:** independent review found no issues in timestamp ownership, migration scope, timer cleanup or rotation/replay assertions. Identity implementation and lifecycle checks are unchanged.
