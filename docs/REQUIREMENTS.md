# Project: Flowboard — a self-hosted project management app (hobby project)

I'm building a personal side project: a mini ClickUp / Asana / Linear-style app. I want to learn good architecture while building it, so design it like a system that could grow, but keep the scope hobby-sized. Please work as a senior engineer pair-programming with me.

## How I want you to work

1. **Plan first, code second.** Before writing any code, produce `docs/PLAN.md` containing: architecture overview, data model, module boundaries, API conventions, and a phased task list.
2. **Split work into small tasks.** Each task must have: ID, title, goal, files touched, acceptance criteria, and dependencies. Save them as `docs/TASKS.md` with checkboxes.
3. **Execute in order, one task at a time.** After each task: run build, lint, and tests, fix failures, tick the checkbox, and give me a 3-line summary. Stop and ask me only when a decision is truly ambiguous; otherwise choose a sensible default and record it in `docs/DECISIONS.md`.
4. **Commit per task** with conventional commit messages.
5. **Write tests as you go**, not at the end. Do not just write happy-path tests; the edge cases listed below are the point.
6. Never leave placeholder or fake implementations without a `TODO` and an entry in `docs/TASKS.md`.

## Tech stack (fixed)

- **Monorepo:** Turborepo + pnpm workspaces
  - `apps/web`: Next.js (App Router) + TypeScript
  - `apps/api`: NestJS + TypeScript
  - `packages/api-client`: generated client (Hey API / `@hey-api/openapi-ts` with the TanStack Query plugin), generated from the NestJS OpenAPI spec
  - `packages/shared`: shared types/constants/zod schemas if useful
  - `packages/tsconfig`, `packages/eslint-config`: shared config
- **UI:** MUI (with a theme, dark mode optional), drag-and-drop via `@dnd-kit`
- **Data fetching:** TanStack Query using the hooks generated by Hey API. Never hand-write API calls that the generator can produce.
- **DB:** PostgreSQL in Docker, using Prisma or TypeORM (pick one, record the choice), with migrations checked in
- **Cache / pub-sub / queue:** Redis in Docker
- **Realtime:** WebSockets (NestJS gateway with Socket.IO) using the Redis adapter so it scales horizontally
- **Async work:** BullMQ on Redis for a worker (activity feed writer / search-index stub)
- **Everything runs with `docker compose up --build`:** services `web`, `api`, `worker`, `postgres`, `redis`. Include `.env.example`, health checks, and automatic migrations + seed on first boot.

## Product requirements

### 1. Auth and multi-tenancy
- Email + password signup/login; hash with argon2 or bcrypt.
- JWT access token (short-lived) + refresh token (httpOnly cookie, rotated). Guards on every route; 401 for unauthenticated, 403 for forbidden.
- Creating an account creates a **workspace (tenant)**; users can be invited/added to a workspace with a role (`admin` | `member`).
- **Every tenant-owned table has `workspaceId`** and every query is scoped by it, enforced in one central place (a repository/base-service layer or Prisma extension / TypeORM subscriber), not ad hoc. Add a test proving tenant A can never read tenant B's data.
- The server resolves identity and role from the token and DB, never from the request body.
- Document in the README how this would swap to OIDC in production.

### 2. Hierarchy
`Workspace > Space > Folder > List > Tasks`
- Node fields: `id, name, type, parentId, position, archivedAt`
- Valid parents: workspace → space → folder → list (lists hold tasks only). Validate in the service layer.
- CRUD for each container, reorder siblings (fractional indexing or explicit move API), soft-delete via `archivedAt` (document this).

### 3. Tasks
Fields: `id, title (max 500), description (markdown), statusId, priority (urgent|high|normal|low|none), assigneeIds[], dueDate, customFields (map fieldKey → value), position, primaryListId, createdAt, updatedAt`.
Operations: CRUD, change status, reorder within column, move between lists (re-validates status and custom fields against the destination list), set/clear custom field values with type validation.

### 4. Scoped statuses
- Status: `id, key, name, category (not_started|active|done|closed), color, position, ownerType (workspace|space|folder|list), ownerId`.
- Resolution: walk list → folder → space → workspace default. Use a clear **merge-by-key** model: a child can inherit, override name/color/position, add new statuses, or hide inherited ones. Document the exact algorithm in the README.
- Every resolved set must contain at least one `not_started`, one `active`, one `done`. Enforce on every mutation.
- Endpoint: `GET /v1/lists/:id/resolved-statuses`. The board and all validators use it.
- Edge cases to handle AND test:
  - Moving a task to a list whose resolved set lacks its status → choose a policy (e.g. map to the destination's first status in the same category, otherwise reject). Test both outcomes.
  - Deleting/disabling a status still used by tasks → block or archive-and-remap. Assert no orphaned board state.
  - Two sibling lists under the same folder with different status sets both render correctly.

### 5. Custom fields
- Definition: `id, key, name, type (text|number|single_select|multi_select|date|checkbox), required, options[{id,label,color}], ownerType (space|folder|list), ownerId, position`.
- Resolved schema for a list = ancestors + local. Key collisions: the nearest owner wins and this is explicit and documented.
- Validate task values against the resolved schema on create/update/move. Errors return 400 with field path in `details`.
- Edge cases to handle AND test: wrong type, select value not in options, missing required field on create, moving a task to a list with a required field it lacks (reject or require values in the move payload), deleting a definition in use (block or keep orphan values, documented).

### 6. Views (Next.js + MUI)
- **Sidebar:** collapsible tree workspace → spaces → folders → lists. Selecting a list loads it.
- **Kanban:** columns = resolved statuses for the list; cards show title, assignee initials, priority badge, due date, optional custom-field chip. Drag between columns changes status; drag within a column changes position. Use optimistic updates with rollback on error.
- **List view:** table with title, status, assignees, priority, due date, and at least two custom field columns. Sort by due date and priority; filter by one custom field.
- **Task detail drawer:** built-in fields plus inputs for resolved custom fields.
- **Config UI:** manage statuses and custom fields at the space/folder level and list level, with a clear "inherited vs local" indicator.
- **Realtime:** when anyone moves or edits a task, other open clients update via WebSocket.
- **Activity feed:** a task status change emits an event → BullMQ worker → stored activity → shown in the task drawer.

### 7. Permissions
- Grants on a container: `{ resourceId, userId, mode: allow | deny }`. Containers are `public` (visible to all workspace members unless denied) or `private` (visible only with an explicit allow). Admins bypass.
- Tree API returns only nodes the caller can see. Denied resource access → 403.
- Status/custom-field config changes: admin or member with edit access on that container (document the choice).
- Enforce permissions in one NestJS guard + a `PermissionService` (not scattered in controllers). Note in the README how team-based grants could be added later.

### 8. API standards
- REST under `/v1`, resource-oriented URLs, consistent error shape `{ error: { code, message, details? } }` via a global exception filter, cursor pagination on list endpoints.
- Full OpenAPI via `@nestjs/swagger`. Every DTO/response must be typed so Hey API produces a clean client. Add a script `pnpm gen:api` that exports the spec and regenerates `packages/api-client`.

### 9. Second channel
Besides the web UI, add a small `scripts/curl-cookbook.md` (or a tiny CLI) that logs in and hits the same API, plus documented webhook payload examples for "task updated". Document which contracts are shared and what is UI-only.

### 10. Seed data
1 workspace, 2 spaces, 2 folders, 3 lists; default statuses at the workspace level plus at least one list that overrides/extends; at least 3 custom fields across 2+ levels (including one `single_select` and one `required`); 20+ varied tasks; users Alice (admin), Bob and Carol (members) with different grants and one private container. Add a second tenant with its own data to exercise isolation.

## Additional packages (replace the monorepo section of the earlier prompt with this)

Use Turborepo + pnpm workspaces. Each package has one job, a `package.json` with `exports`, its own `tsconfig` extending the shared config, and a build step that Turbo caches.

### `packages/contracts` (shared data between UI and backend)
- Single source of truth for domain shapes: zod schemas, inferred TS types, enums, and constants.
- Contents: node types (`workspace|space|folder|list`), priorities, status categories, custom field types, permission modes, pagination envelope, error shape `{ error: { code, message, details? } }`, error code enum, WebSocket event names + payload schemas, and request/response schemas for tasks, statuses, fields, and grants.
- Pure TypeScript with no framework imports (no Nest, no React), so both sides can use it.
- Backend: use `nestjs-zod` so the DTOs and validation pipes are built from these schemas, which also feeds Swagger.
- Frontend: use the same schemas with `react-hook-form` + `zodResolver` for forms (task create, status config, custom field config).
- Include pure logic worth sharing and unit testing, such as the status-resolution and custom-field-resolution algorithms (as pure functions over plain arrays). The API calls them with DB data, and the UI can reuse them for previews like "inherited vs local".

### `packages/openapi` (Swagger package)
- Contains a script that boots the NestJS app in "spec only" mode (no DB connection needed), builds the document with `@nestjs/swagger`, and writes `openapi.json` into this package.
- The Swagger UI is served at `/docs` in the API for humans; the committed `openapi.json` is for tools.
- Add a CI-style check `pnpm openapi:check` that regenerates the spec and fails if it differs from the committed file, so the contract can't drift silently.
- Add Spectral (or a similar linter) rules to enforce conventions: `/v1` prefix, consistent error responses, cursor pagination on list endpoints, `operationId` on every operation (needed for clean generated hook names).

### `packages/api-client` (generated)
- Generated by `@hey-api/openapi-ts` from `packages/openapi/openapi.json`, with the TanStack Query plugin, and the zod plugin if useful.
- Output is git-ignored or committed (pick one, record in DECISIONS.md), never hand-edited.
- Exports: SDK functions, types, and `queryOptions` / `useMutation` helpers.
- Add a `setupClient()` helper that configures base URL, credentials (cookie refresh), and a response interceptor that handles 401 → refresh token → retry once.
- Turbo pipeline order: `contracts` → `api` (spec export) → `openapi` → `api-client` → `web`. `pnpm gen:api` runs the middle steps.

### `packages/ui` (shared components)
- MUI-based component library used by `apps/web`, plus a Storybook (or a simple playground page) for development.
- Contains the theme (light/dark, tokens), and reusable presentational components that don't know about the API: `StatusChip`, `PriorityBadge`, `AssigneeAvatarGroup`, `DueDateLabel`, `CustomFieldInput` (renders by field type), `CustomFieldChip`, `KanbanColumn`, `KanbanCard`, `TreeView` item, `ConfirmDialog`, `EmptyState`, `ErrorState`, form field wrappers.
- Components take plain props (use types from `contracts`), no data fetching inside. Data-aware components live in `apps/web`.
- Export a single `ThemeProvider` wrapper for Next.js App Router (including the MUI emotion cache setup for SSR).

### Other shared packages
- `config-typescript`: base, nest, and next tsconfigs.
- `config-eslint`: shared flat config with import ordering and a rule that forbids `apps/web` from importing `apps/api` and vice versa.
- Add `eslint-plugin-boundaries` (or the equivalent) so apps may import packages but packages may not import apps, and `contracts` may not import anything.

### Docker
- Multi-stage Dockerfiles using `turbo prune --docker` for `api`, `worker`, and `web` so images only include the needed workspaces.
- Compose services: `web`, `api`, `worker`, `postgres`, `redis`. Healthchecks, `depends_on: condition: service_healthy`.
