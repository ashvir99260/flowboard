## Patterns worth adapting

### ClickUp: containment, settings and views are different things

A List is a task container; List view is a presentation. Flowboard should similarly keep `primaryListId` independent of whether the user opens Board or List. Its required hierarchy remains strictly Workspace → Space → Folder → List → Task. ClickUp's optional nesting/subfolders do not expand our scope. [ClickUp hierarchy](https://help.clickup.com/hc/en-us/articles/13856392825367-Intro-to-the-Hierarchy)

ClickUp's API exposes custom-field definitions separately from task values, including stable option IDs. Flowboard uses its own six field types, inherited definitions and strict validators; it must not derive option identity from a displayed label. This is a public contract pattern, not an inference that ClickUp stores JSONB. [Custom Fields API](https://developer.clickup.com/docs/customfields)

### Asana: asking for data and keeping it current are separate paths

LunaDb loads data and subsequent updates. Its published evolution separates connection state from loading, and discusses the ordering problems introduced by distributed invalidation. Flowboard can use the same separation of responsibilities with REST reads and permission-scoped WebSocket invalidations, without implementing LunaDb or its query language. [LunaDb engineering](https://asana.com/resources/scaling-lunadb)

Asana's EAV design enables flexibility but requires additional physical indexes and operational machinery. Flowboard's built-in task properties are known, so normal relational columns are easier to constrain; JSONB is limited to custom values and event payloads. This storage choice is our recommendation, not Asana's implementation. [Asana database trade-offs](https://asana.com/inside-asana/database-architecture-sharding-scaling)

Asana's public task model supports multi-project membership. Flowboard deliberately has one primary list, making status resolution, ordering and access easier to reason about. It also keeps stricter field-deletion behavior than Asana's disabled historical values. [Object hierarchy](https://developers.asana.com/docs/object-hierarchy), [Custom fields](https://developers.asana.com/docs/custom-fields-guide)

### Linear: coherent interaction and immediate feedback

Linear's UI work emphasizes consistent headers, sidebar, panels and visual hierarchy. Its **12 March 2026** refresh reduces competing navigation emphasis. Flowboard will use a stable shell, one board/list toolbar and a detail drawer with MUI semantic tokens. This adapts interaction principles rather than copying branding. [2024 design explanation](https://linear.app/now/how-we-redesigned-the-linear-ui), [2026 refresh](https://linear.app/now/behind-the-latest-design-refresh)

Board and List should share data, filters and mutations. Keyboard/button alternatives should use the same commands as drag-and-drop. Linear's documented board interactions provide a useful precedent; Flowboard's exact accessibility acceptance remains its own. [Board layout](https://linear.app/docs/board-layout), [Display options](https://linear.app/docs/display-options)

Linear publicly discusses a proprietary realtime sync engine, and its product documents offline retry behavior. Flowboard borrows immediate optimistic feedback with version checks and rollback. It does **not** add persistent offline writes or a browser database replica: those need a separate conflict model and are outside MVP. [Sync-engine talk, 29 June 2023](https://linear.app/now/scaling-the-linear-sync-engine), [Offline behavior](https://linear.app/docs/get-the-app)

## Chosen architecture and alternatives

| Approach                                                                       | Benefit                                                              | Cost for this project                                                                               | Decision                                                        |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Modular API, relational DB, generated REST, optimistic UI, invalidation events | Clear transactions, learnable boundaries, one authoritative database | Refetches after events; coarse tenant write serialization initially                                 | **Use now**, matching the fixed stack.                          |
| Full client replication and offline mutation queue                             | Rich disconnected interaction and local reads                        | Bootstrap/partial replication, permission revocation, conflict resolution and durable sync protocol | Separate future project; not a shortcut to optimistic updates.  |
| Distributed domain services and tenant shards                                  | Independent scaling at large operational volume                      | Distributed consistency, deployment/debugging overhead, shard operations                            | Preserve module boundaries; split only after measured pressure. |

The recommendation is a ClickUp-like hierarchy, Linear-like interaction model, and explicit read/update separation inspired by Asana, implemented with Flowboard's existing stack. We are not claiming these companies use NestJS, Prisma, TanStack Query or our proposed schema.

## Source and scope rules

- Engineering posts support only their described architecture and date. Public API/help pages establish visible behavior, not private implementation.
- No binaries, private accounts or traffic captures were used. REA is unnecessary for this public-document research.
- Integration webhooks are not evidence of internal WebSocket delivery or exactly-once processing. Flowboard's outbox/worker contract is specified independently.
- No source justifies adding billing, multi-list membership, subtasks, offline sync, a custom query engine or a distributed cache to this MVP.
- Revisit dated claims before making a vendor-specific operational decision. Flowboard's implementation tests remain the authority for its behavior.
