# API feature rules

Read the [root instructions](../../AGENTS.md), [backend guide](../../docs/BACKEND_GUIDELINES.md), [backend contracts](../../docs/BACKEND_CONTRACTS.md) and current task before changing this application. These rules specialize the root harness for NestJS; they do not replace it.

- Group domain code under `src/modules/<feature>/`, with one feature module and its controller/service (D93). Keep `modules/auth/` and `modules/platform/` flat: grouped DTOs, feature config and tests live directly beside source files (D89/D90/D92). Other features may use focused DTO or mapper/read-model subfolders only for real code. Do not create root-level controllers/services/DTOs directories, a pass-through ModulesModule or empty future modules.
- Use `src/core/config/` for reusable application/Redis settings, `src/core/utils/` for pure helpers and `src/core/common/` for decorators, errors, filters, DTO adapters, injection tokens and Swagger support (D96). `src/shared/` owns shared Nest modules and their providers. SharedModule wires global filter/validation/serialization once and imports `shared/logging/`; AppModule composes it with PlatformModule and AuthModule. Core cannot import shared or feature modules; shared cannot import feature modules. Shared lint enforces these directions, including type imports and re-exports. Keep auth settings/runtime in `modules/auth/`. Register each connection lifecycle once; add no empty aggregator modules or duplicate providers. Persistence remains in `packages/database`.
- `createApplication` uses an explicit `ExpressAdapter` for runtime and spec export. Preserve Express request/response, parsing, cookie, CORS and error behavior; do not introduce Fastify or a second bootstrap path.
- Use Nest constructor injection and explicit module imports. Export only providers/tokens another feature needs. Avoid circular dependencies and routine `forwardRef()`; resolve ownership rather than hiding cycles with a global module.
- Controllers own transport/decorators; services own use-case orchestration. Raw Prisma/SQL, Prisma/PostgreSQL connection construction, locking and scoped repositories belong only to `packages/database`. API runtime providers may own Redis clients with explicit shutdown. Shared pure rules and Zod schemas belong to `packages/contracts`. Never move these into an API feature to imitate the article's ORM examples.
- Group related DTO classes by feature and request/response role, such as `auth.request.dto.ts`, `auth.response.dto.ts` and `health.response.dto.ts` (D92); avoid one file per small adapter. DTO classes extend `createZodDto` from shared schemas. Keep persistence/read models separate and explicitly project safe responses. Do not duplicate schema fields using `@ApiProperty`/class-validator or serialize entire database entities.
- Each endpoint includes guard metadata, unique `operationId`, summary/description, typed success/error responses, and schema-valid examples. Schema fields/models have titles/descriptions/examples in Zod metadata. Use `@ZodResponse`; supplemental payload `@ApiResponse` declarations preserve `type: ResponseDto.Output`. A 204 has no JSON body. Document headers/security faithfully and use only synthetic credentials in examples.
- Preserve central authentication and PermissionGuard/PermissionService policy, tenant context, transaction rechecks and outbox guarantees. The global error envelope and DTO serialization apply to every feature. Spec-only bootstrap uses the same real controller registry without service connections or listeners.
- Regenerate spec/client with `pnpm gen:api`, run `pnpm openapi:check`, and verify concrete response schema references. Generated files are never hand-edited; frontend consumers use the generated API client.
- Keep kebab-case filenames, PascalCase classes/types and explicit `.js` relative ESM imports. Prefer `const` and clear typed data transformations. Use dispatch objects for natural mappings and ordinary branches when clearer; avoid style-driven complexity.
- Keep the API's native ESM build and shared verbatim module syntax. Use type-only imports for types and `import.meta.resolve` for CLI resolution; do not introduce CommonJS loading or exports (D95).
- Leave one blank line after each export statement/declaration, including an exported NestJS module class, before the next statement or its decorators. Keep decorators attached to their declaration. EOF needs only the final newline; do not add trailing empty lines. Shared ESLint presets enforce this rule.
- Auth/platform tests live directly beside their source as `*.unit.spec.mjs` or `*.integration.spec.mjs`, with no test subfolders (D90). Jest discovers `src/**/*.spec.mjs` plus the retained common suites in `test/unit/**/*.spec.mjs` and `test/integration/**/*.spec.mjs`; Node runs `test/bootstrap/*.test.mjs`. All feature tests import compiled ESM from `dist`. Tests are excluded from production output and Docker context. Put shared fixture factories in `test/common/` with no global hooks or mutable singleton resources. Each integration suite owns isolated containers and cleans up its app before infrastructure, even on setup failure. Keep the existing `.mjs` runner; `.spec.ts` is unsupported without a separately verified runner change.
- Use the injected logger from `shared/logging` for semantic operation events. The shared Pino-backed `@flowboard/logger` emits JSON with generated request IDs and verified identity only. Never pass request bodies, headers, query strings, URLs, SQL/parameters, arbitrary errors/messages/stacks or credentials to logs. Use static operation names and safe status/error codes; debug tracing is runtime configurable. See [logging guide](../../docs/LOGGING.md).
- Run the root quality gates and task evidence workflow. These intra-API folder rules are review conventions, not a newly implemented automated lint checker.
