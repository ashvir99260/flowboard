# API feature rules

Read the [root instructions](../../AGENTS.md), [backend guide](../../docs/BACKEND_GUIDELINES.md), [backend contracts](../../docs/BACKEND_CONTRACTS.md) and current task before changing this application. These rules specialize the root harness for NestJS; they do not replace it.

- Group domain code under `src/<feature>/`, with one feature module and its controller/service. Put focused request/query/path/response adapters in `<feature>/dto/`. Add mapper/read-model subfolders only for real code. Do not create root-level controllers/services/DTOs directories or empty future modules.
- Use `platform/` for genuinely shared HTTP/bootstrap infrastructure. Keep auth settings/runtime in `auth/`. `AppModule` composes modules, and global guards/pipes/interceptors/filters and connection lifecycles are registered once. Current auth/platform extraction is tracked by P02-06; do not claim it already exists.
- Use Nest constructor injection and explicit module imports. Export only providers/tokens another feature needs. Avoid circular dependencies and routine `forwardRef()`; resolve ownership rather than hiding cycles with a global module.
- Controllers own transport/decorators; services own use-case orchestration. Raw Prisma/SQL, Prisma/PostgreSQL connection construction, locking and scoped repositories belong only to `packages/database`. API runtime providers may own Redis clients with explicit shutdown. Shared pure rules and Zod schemas belong to `packages/contracts`. Never move these into an API feature to imitate the article's ORM examples.
- DTO classes extend `createZodDto` from shared schemas. Keep persistence/read models separate and explicitly project safe responses. Do not duplicate schema fields using `@ApiProperty`/class-validator or serialize entire database entities.
- Each endpoint includes guard metadata, unique `operationId`, summary/description, typed success/error responses, and schema-valid examples. Schema fields/models have titles/descriptions/examples in Zod metadata. Use `@ZodResponse`; supplemental payload `@ApiResponse` declarations preserve `type: ResponseDto.Output`. A 204 has no JSON body. Document headers/security faithfully and use only synthetic credentials in examples.
- Preserve central authentication and PermissionGuard/PermissionService policy, tenant context, transaction rechecks and outbox guarantees. The global error envelope and DTO serialization apply to every feature. Spec-only bootstrap uses the same real controller registry without service connections or listeners.
- Regenerate spec/client with `pnpm gen:api`, run `pnpm openapi:check`, and verify concrete response schema references. Generated files are never hand-edited; frontend consumers use the generated API client.
- Keep kebab-case filenames, PascalCase classes/types and explicit `.js` relative ESM imports. Prefer `const` and clear typed data transformations. Use dispatch objects for natural mappings and ordinary branches when clearer; avoid style-driven complexity.
- API tests currently run built ESM through `test/**/*.spec.mjs` (Jest) and top-level `test/*.test.mjs` (Node startup tests). Group tests by feature within those patterns. Source-colocated `.spec.ts` files will not run without a separately verified runner change.
- Run the root quality gates and task evidence workflow. These intra-API folder rules are review conventions, not a newly implemented automated lint checker.
